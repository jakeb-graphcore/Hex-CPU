--------------------Hex CPU Verif Tutorial--------------------

The repository contains a number of verification tasks for those new to verification to understand some of the components required in a testbench for a design.
The design for this task is the hex cpu (see hex.pdf for the specification). The first task in this tutorial will be a design rather than a verification task, to design the hex cpu.
You may, however, want to try out your testbench on another person's design. The testbench is wrapped in Python using a package called cocotb (see https://www.cocotb.org/).
Most of the components in the testbench have already been created. You shouldn't have to tweak any of existing fully implemented components to complete the tasks, but you are free
to edit them as you wish. See verif_tb/README.txt for more information on the testbench.

----------Task 1 (RTL)----------

Relevant files: hex.pdf, verif_tb/designs/my_cpu.sv, icarus_tb/icarus_tb.sv
1. Write the RTL for the hex cpu design described in the hex cpu spec (see hex.pdf).
2. Implement a small testbench in icarus_tb/icarus_tb.sv and write some directed tests for your design.
3. cd into icarus_tb and then run ./run_tb.sh my_cpu

----------Task 2 (Arch Monitor and Checker)----------

Relevant files: verif_tb/arch_monitor.sv, verif_tb/monitors.py
Currently the testbench has a single checker on the data memory interface. However, this does not check that the architectural state of the cpu (e.g. registers pc, oreg, .etc) are
updated correctly. Your task is to implement the SystemVerilog side of an architectural state checker. The cocotb monitor in verif_tb/monitors.py is already setup to check that the
state matches our model. You have to do the following:
1. Ensure scoreboards are enabled. Set data_enable_scoreboard, data_read_scoreboard_enabled and data_end_of_test_scoreboard_check to True in verif_tb/tb_config.py.
2. Instantiate the arch monitor in testbench and name it `u_arch_monitor`.
3. Enable the checker by setting setting use_arch_state_monitor in verif_tb/tb_config.py to True.
4. Collect arch state information from the dut by filling in arch_monitor.sv

----------Task 3 (Functional Coverage)----------

Relevant files: verif_tb/monitors.py, verif_tb/coverage.py
Before we begin extensively testing, it's useful to consider what behaviour of the design we wish to test. We also want to automatically check whether are current tests are covering
this behaviour. This is what functional coverage is used for. An example coverpoint, which checks we have seen every instruction executed, is given in verif_tb/coverage.py. If you
run a regression with the arch monitor enabled, you can see the coverage results summary in verif_tb/sim_logs/coverage_results.log, with more detail in verif_tb/sim_logs/coverage.log. You have to do the following:
1. Define coverpoints that cover all the functionality in the design.
2. Write code to collect this coverage using the arch monitor (you can edit the SystemVerilog arch monitor to collect more information from the design if you wish).

----------Task 4 (Testgen)----------

Relevant files: verif_tb/testgen.py
Now that functional coverage has been defined, we need tests that will hit this coverage. An example of two directed tests are given in verif_tb/testgen.py. Each one returns a list
of instructions to load into instruction memory and be executed during simulation. The issue with these are that they are fixed. We should create some tests that randomise the
instructions generated. You have to do the following:
1. Create a number of randomised tests.
2. Ensure that these tests hit 100% of coverage. (You may need to increase the number of tests run by editing verif_tb/tb_config.py).

----------Task 5 (Dynamic instruction generation)----------

Relevant files: verif_tb/transactors.py, verif_tb/monitors.py
Currently, our testbench loads instructions into memory before we start simulating, and this instruction memory remains static throughout the simulation. However, we control the
instruction memory ports, so we can potentially drive into the design any instruction we want at any time. We can do this by replacing the instruction memory transactor with a dynamic
instruction driver. In particular, this driver should make generating tests with branch instructions a lot easier. You have to do the following:
1. Set the following tb_config options
use_dynamic_instruction_transactor = True
data_enable_scoreboard = False
data_read_scoreboard_enabled = False
data_end_of_test_scoreboard_check = False
2. Fill in the code for the dynamic instruction transactor in verif_tb/transactors.py
3. Edit the arch monitor to use instructions generated by the dynamic instruction transactor rather than the instruction memory transactor.
